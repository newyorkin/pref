# pref

Онлайн-преферанс для трёх игроков: стол по приглашению, торговля, розыгрыш и автоматический подсчёт пули. Интерфейс на русском языке.

Проект состоит из независимого игрового движка на TypeScript, сервера HTTP/WebSocket с SQLite и веб-клиента на React.

## Возможности

- Регистрация, вход и создание стола со ссылкой-приглашением.
- Согласование договорённостей перед первой сдачей. Во время партии кнопка «Договорённости» показывает их любому игроку без возможности изменить.
- Контракты от шестерной до десятерной, игры без козыря, мизер и распасы.
- Вист в светлую и в тёмную, полвиста и уход без трёх.
- Пуля, гора, висты, история сдач и выгрузка результатов в текстовый файл.
- В выгруженном файле результатов для каждой контрактной сдачи после заказа указано, как ответил каждый защитник: вист, пас, полвиста или возврат виста, а у единственного вистующего — в светлую или в тёмную, например «Борис — вист в светлую, Вера — пас». Игроки названы по местам, поэтому файл одинаков у всех, кто его выгрузил.
- В пуле записи последней сдачи в пулю, гору и висты всех игроков выделены синим, чтобы отличать их от накопленных. Со следующей записью выделение переходит к ней, а прежние числа остаются в цепочке обычным цветом.
- Имя каждого игрока со счётом записано в пуле на отдельной строке горы, ближней к игроку, и не перекрывает записи. Длинное имя пишется мельче, а если не помещается и так, сокращается многоточием; полное имя видно во всплывающей подсказке. Длинная цепочка записей в пуле, горе или вистах переносится на следующую строку своей области, а не уменьшается до нечитаемого размера.
- Окно пули занимает всё доступное место на экране с сохранением пропорций, на телефоне тоже. На низком горизонтальном экране, например на телефоне, повёрнутом набок, кнопка «Закрыть» стоит сбоку от пули, чтобы пуля занимала всю высоту. Если размер окна пули изменён вручную, он запоминается, но окно не становится больше экрана, так что пуля не обрезается. Двойное нажатие на уголок изменения размера, мышью или пальцем, возвращает размер по экрану.
- Итог сдачи: после завершения сдачи открывается окно с записью каждого игрока в пулю, гору и висты и с раскладом. Кнопка «Итог сдачи» открывает его снова до первой взятки следующей сдачи и после конца партии.
- Окончательный заказ показывается рядом с именем разыгрывающего у соперников и в треугольнике взяток. Во время сноса и заказа вверху стола подписана заявка, выигравшая торговлю, чтобы её не путали с заказом; все заявки остаются в логе.
- Сдающий отмечен в треугольнике взяток у всех трёх игроков, в том числе у самого сдающего. У соперника, который сдавал, пометка «(сдавал)» стоит и рядом с именем над его картами.
- Настройки отображения карт, порядка руки и паузы после взятки; они сохраняются в браузере отдельно для каждого игрока.
- Повторное подключение к текущему столу при временном разрыве связи.

**Столы и партии сохраняются в SQLite и восстанавливаются после перезапуска сервера.** Снимок содержит полное серверное состояние, рассадку, договорённости, подтверждения и обработанные идентификаторы команд. Для восстановления необходимо сохранить тот же файл БД или Docker-том.

## Требования

- Node.js 22 или новее; в `.nvmrc` указана ветка 22. Сервер использует встроенный модуль `node:sqlite`.
- pnpm **10.18.3**, как указано в `package.json`.
- Git для получения исходников.
- Docker с Compose — для запуска в контейнере вместо локальной установки Node.js.

Если Corepack доступен в установленном Node.js, включить нужный pnpm можно так:

```sh
corepack enable
corepack prepare pnpm@10.18.3 --activate
pnpm --version
```

Если команды `corepack` нет, установите pnpm 10.18.3 удобным для вашей системы способом.

## Быстрый старт для разработки

```sh
git clone https://github.com/newyorkin/pref.git
cd pref
pnpm install --frozen-lockfile
pnpm dev
```

Откройте [http://localhost:5173](http://localhost:5173).

Команда `pnpm dev` запускает два процесса:

| Процесс | Адрес | Назначение |
| --- | --- | --- |
| Vite | `http://localhost:5173` | Интерфейс и обновление клиента при изменении кода |
| Сервер | `http://127.0.0.1:3001` | HTTP API, WebSocket и SQLite |

Vite проксирует запросы API и `/ws` на сервер. Адрес прокси задан в [packages/web/vite.config.ts](packages/web/vite.config.ts); если меняете порт сервера, обновите и его.

Если ваша версия Node.js требует флаг для `node:sqlite`, задайте `NODE_OPTIONS=--experimental-sqlite` перед запуском. Например, в PowerShell:

```powershell
$env:NODE_OPTIONS = "--experimental-sqlite"
pnpm dev
```

### Как начать игру

1. Зарегистрируйтесь и войдите. Пароль должен содержать не менее восьми символов, цифру и символ, не являющийся буквой или цифрой.
2. Создайте стол, выбрав длину пули и договорённости.
3. Передайте ссылку-приглашение двум другим игрокам. Каждый входит под своим именем и занимает свободное место.
4. Приглашённые игроки подтверждают договорённости. Если хозяин изменит настройки, подтверждения сбросятся.
5. После двух подтверждений хозяин запускает первую сдачу. С этого момента настройки стола заблокированы.
6. Выполняйте доступные действия на столе. Сервер проверяет очередь хода и допустимость каждого действия.

Для проверки втроём на одном компьютере используйте отдельные профили браузера или разные браузеры: вкладки одного профиля используют общую сессию.

### Тест втроём в одной вкладке

Для ручной проверки без трёх браузеров включите локальный тестовый режим. В PowerShell перед запуском:

```powershell
$env:LOCAL_TEST_MODE = "1"
$env:HOST = "127.0.0.1"
pnpm dev
```

Откройте [тестовый стол](http://localhost:5173/testing) или ссылку «Тест втроём в одной вкладке» на главной странице. Выберите договорённости и нажмите «Начать тест втроём»: регистрация и подтверждения не нужны.

- «Игрок 1 / 2 / 3» переключают собственную руку и вид стола. Ручное переключение выключает автопереход.
- «Кто ходит» показывает игрока с доступным действием и переключает на него. «Автопереход» делает это после каждого принятого действия.
- Все действия выполняются вручную через обычный игровой интерфейс. Настройки отображения доступны в верхней панели.
- «Новая партия» удаляет текущую тестовую партию и возвращает к выбору договорённостей. Обновление страницы в той же вкладке восстанавливает текущий тест.

Это отдельные партии в памяти: они не создают пользователей и обычные столы, не меняют их сессии и пропадают при перезапуске сервера или после суток бездействия. Доступны три персональных представления для ручной игры за всех; правила, проверка действий и раздача карт выполняются сервером как обычно. Ботов и одновременного показа трёх столов в этом режиме нет.

По умолчанию режим выключен. С `LOCAL_TEST_MODE=1` сервер разрешает только loopback-адрес; API теста отклоняет чужой Origin и публичный Host, в том числе при проксировании. Для собранного клиента используйте тот же флаг с обычным запуском сервера и адрес `http://127.0.0.1:3001/testing`. Для возврата к обычному запуску удалите переменную: `Remove-Item Env:LOCAL_TEST_MODE`.

## Запуск через Docker

Из корня репозитория:

```sh
docker compose up --build -d
docker compose logs -f pref
```

Откройте [http://localhost:3001](http://localhost:3001). Контейнер собирает клиент и раздаёт интерфейс, HTTP API и WebSocket с одного порта.

SQLite находится в `/data/pref.sqlite`. Каталог `/data` подключён к именованному тому Compose `pref-data`.

Остановка:

```sh
docker compose down
```

Эта команда сохраняет том с БД. Команда `docker compose down -v` удаляет и том, включая учётные записи и сессии. При остановке процесса клиентам потребуется переподключение; партия восстановится из сохранённого снимка.

## Сборка и запуск без Vite

Сначала установите зависимости, затем соберите клиент:

```sh
pnpm --filter @pref/web build
```

Пример запуска из корня репозитория в PowerShell:

```powershell
$env:STATIC_DIR = (Resolve-Path .\packages\web\dist).Path
$env:DATABASE_PATH = Join-Path $PWD.Path "pref.sqlite"
$env:HOST = "127.0.0.1"
$env:PORT = "3001"
$env:NODE_OPTIONS = "--experimental-sqlite"
pnpm --filter @pref/server start
```

Откройте [http://localhost:3001](http://localhost:3001). Сервер запускается через `tsx`; отдельной команды компиляции серверного пакета сейчас нет.

## Конфигурация сервера

Переменные окружения читает [packages/server/src/main.ts](packages/server/src/main.ts). Автоматическая загрузка `.env` не настроена: задавайте переменные средствами оболочки или Compose.

| Переменная | По умолчанию при локальном запуске | Назначение |
| --- | --- | --- |
| `HOST` | `127.0.0.1` | Адрес прослушивания |
| `LOCAL_TEST_MODE` | `0` | `1` включает изолированный тест втроём на `/testing`; сервер должен слушать loopback-адрес |
| `PORT` | `3001` | Порт HTTP и WebSocket |
| `DATABASE_PATH` | `pref.sqlite` | Путь к SQLite; относительный путь считается от рабочего каталога серверного процесса |
| `STATIC_DIR` | Не задана | Каталог собранного клиента; без него сервер не раздаёт интерфейс |
| `COOKIE_SECURE` | `0` | Значение `1` добавляет Secure к cookie; используйте за HTTPS-прокси |
| `PUBLIC_ORIGIN` | Схема запроса и заголовок Host | Канонический origin интерфейса, например `https://pref.example.com`, для проверки WebSocket Origin |

При `pnpm --filter @pref/server start` или `dev` рабочим каталогом является `packages/server`. Абсолютные пути позволяют явно выбрать расположение БД и сборки клиента.

В Docker используются `HOST=0.0.0.0`, `DATABASE_PATH=/data/pref.sqlite` и `STATIC_DIR=/app/packages/web/dist`.

## Безопасность и восстановление

- Каждая серверная сдача независимо перемешивается Fisher–Yates с `node:crypto.randomInt`. Порядок следующих сдач не выводится из начального seed пули.
- Числовой seed остаётся только детерминированным API движка для тестов. Производственный сервер передаёт готовую раздачу при старте и при каждом переходе к следующей сдаче.
- `POST /tables/:id/deal` игнорирует устаревшее клиентское поле `seed`. WebSocket-действие новой партии имеет вид `{ "type": "rematch" }`; действие `rematch` с полем `seed` отклоняется. При обновлении публикуйте сервер и клиент вместе.
- Сессии действуют 30 дней с продлением при активности. Cookie имеет `HttpOnly`, `SameSite=Strict` и `Max-Age`; Secure добавляется для прямого HTTPS или при `COOKIE_SECURE=1`. HTTP-запросы также обновляют срок cookie.
- Вход и регистрация совместно ограничены: 30 попыток с IP и 10 по имени за минуту. При превышении сервер возвращает `429`. Лимиты хранятся в памяти одного процесса; IP берётся из сетевого соединения, заголовки forwarded не считаются доверенными. За reverse proxy это может объединить клиентов в один IP-лимит; учитывайте это при настройке внешней защиты.
- WebSocket с чужим `Origin` отклоняется при upgrade. Для HTTPS за обратным прокси задайте `COOKIE_SECURE=1` и точный `PUBLIC_ORIGIN`; в Docker добавьте их в `environment` сервиса. Клиенты без Origin по-прежнему должны иметь действующую сессию.
- Heartbeat отправляется каждые 30 секунд, неответившее соединение закрывается. По умолчанию сообщение ограничено 8 КиБ, частота — 50 сообщений за 5 секунд на соединение. Клиент переподключается с экспоненциальной паузой и джиттером до 10 секунд.

При старте сервер применяет упорядоченные миграции из [db.ts](packages/server/src/db.ts); применённые версии записываются в `schema_version`. Перед обновлением сохраните резервную копию БД. После первого обновления старые сессии без срока действия потребуют повторного входа; пользователи сохранятся.

Снимок стола и запись команды фиксируются одной транзакцией до рассылки клиентам. После рестарта восстанавливаются версия и обработанные `actionId`, поэтому повтор ранее принятой команды не выполняется второй раз. Завершённые столы сохраняются 7 дней, остальные неактивные столы — 30 дней после последнего изменения; затем удаляются вместе с журналом команд. Проверка TTL выполняется при старте и раз в минуту. Параметры TTL и транспортных ограничений доступны в `GameServerOptions` для серверной настройки и тестов.

## Правила и договорённости

Ниже описаны правила, реализованные в проекте. Выбор готовой разновидности «Сочи», «Питер» или «Ростов» в интерфейсе не предусмотрен.

### Основные правила

- Колода из 32 карт: от семёрки до туза. Три руки по десять карт и прикуп из двух карт.
- В торговле масти возрастают в порядке ♠, ♣, ♦, ♥, затем без козыря. Новая контрактная заявка должна быть выше предыдущей.
- Мизер перебивает заявки до восьмерной включительно; перебить мизер можно девятерной или десятерной. Игрок, уже заявлявший контракт, не может затем заявить мизер.
- После покупки прикупа разыгрывающий сносит две карты и заказывает игру не ниже допустимого уровня.
- На мизере ловящие видят условную руку разыгрывающего: исходные карты вместе с прикупом, без пометки, какие две снесены. В руке при этом по-прежнему десять карт, и отдельный снос соперникам не отдаётся. Руки ловящих при сносе и заказе закрыты. Они открываются с начала розыгрыша, а если первый ход у разыгрывающего — после его карты. Если разыгрывающий предлагает записать взятки, им показывается уже его настоящая оставшаяся рука. После сдачи прикуп и снос видны в раскладе.
- Три паса до первой заявки приводят к распасам.
- В розыгрыше нужно давать в масть; при её отсутствии — класть козырь, если он есть. Перебивать старшим козырем необязательно.
- При одном вистующем доступен выбор света или темноты. В светлую вистующий управляет также открытой рукой пасующего; при двух вистующих игра идёт в тёмную.
- Разыгрывающий мизера или контракта с одним вистующим, если вист не в тёмную, может предложить записать число взяток, например «6 запишем?». Его оставшиеся карты сразу открываются обоим соперникам, чтобы они видели их до ответа, и остаются открытыми до конца сдачи, даже если предложение отклонено. Предложение вистующего или ловящих на мизере («отдаём 4?») карт не открывает. Пока не ответили оба соперника, автор может отменить своё предложение, даже если один из них уже согласился: данные согласия сбрасываются, розыгрыш продолжается, и автор может сделать новое предложение. Число отмен не ограничено. После последнего ответа отмена невозможна. Реплики «не согласен» и «отменяю» видны над сказавшим их игроком до следующей сыгранной карты, затем остаются только в логе.
- Полвиста доступно второму защитнику на шестерной или семерной после паса первого. Первый защитник может принять полвиста пасом или вернуть обычный вист.
- На распасах карты прикупа задают масть первых двух ходов; сами карты прикупа не участвуют во взятках. Первые три взятки начинает игрок, который был на первом слове, даже если предыдущую забрал кто-то другой. С четвёртой ходит взявший предыдущую.

### Настройки стола

| Поле | Значения | По умолчанию |
| --- | --- | --- |
| `bulletTarget` | Целая длина пули от 3 до 10000 | `10` |
| `raspasProgression` | `111`, `122`, `123`, `123123` | `111` |
| `raspasExit` | `666`, `677`, `788`, `678678` | `666` |
| `throwTalon` | Договорённость «бросить прикуп в лицо» | `false` |

Прогрессия задаёт множитель последовательных распасов:

| Значение | Множители |
| --- | --- |
| `111` | 1, 1, 1, … |
| `122` | 1, 2, 2, … |
| `123` | 1, 2, 3, 3, … |
| `123123` | 1, 2, 3, 1, 2, 3, … |

Выход задаёт минимальный уровень и в торговле, и в окончательном заказе. Заявка ниже этого уровня недоступна и отвергается сервером. Мизер от выхода не зависит.

| Значение | До распасов | После 1-го | После 2-го | После 3-го и далее |
| --- | --- | --- | --- | --- |
| `666` | 6 | 6 | 6 | 6 |
| `677` | 6 | 7 | 7 | 7 |
| `788` | 6 | 7 | 8 | 8 |
| `678678` | 6 | 7 | 8 | Повтор 6, 7, 8, … |

Успешный контракт требуемого уровня или сыгранный мизер сбрасывает индекс распасов. Подсад этого не делает.

При включённом `throwTalon` открытые на контрактной игре тузы прикупа дают сдающему по одному очку в пулю, если разыгрывает кто-то другой. Свою игру сдающий себе за тузов не записывает. Разыгрывающий, который не является сдающим, может бросить прикуп: тогда сдающему записываются два очка в гору. В мизере и распасах запись за тузов не применяется.

В форме также показаны фиксированные договорённости: первый ход в тёмную, жлобский вист и проверяемая десятерная включены; «Сталинград» выключен. Эти пункты сейчас не редактируются.

| 7 | 4 | 2 |
| 8 | 6 | 1 |
| 9 | 8 | 1 |
| 10 | 10 | 0 |

Сыгранный мизер даёт 10 очков в пулю, каждая взятая на мизере взятка — 10 очков в гору. На распасах перед применением множителя из числа взяток каждого игрока вычитается минимальное число взяток за столом; игрок без взяток получает множитель в пулю.

При двух вистующих норма взяток общая: 4 на шестерной, 2 на семерной, 1 на восьмерной и девятерной. Взятки одного закрывают нехватку другого, поэтому при 4 и 1 на шестерной в гору не пишется никому. Если сумма меньше нормы, недобор пишется в гору каждому из двоих. Один вистующий отвечает за всю норму, и в его зачёт входят взятки пасующего.

Партия завершается, когда все трое заполнят пулю. Если записывающему в пулю уже некуда писать и пули обоих соперников тоже заполнены, остаток списывается с его горы. Если горы не хватает, она обнуляется, и каждому из двух соперников в гору пишется только та часть остатка, которую не удалось списать. Например, при горе 8 и остатке 10 гора записывающего становится 0, а соперникам пишется по 2.

Переполнение пули, помощь другим игрокам и итоговый расчёт реализованы в [scoring.ts](packages/engine/src/scoring.ts). Конкретные примеры записей находятся в [scoring.test.ts](packages/engine/src/scoring.test.ts).

## Структура проекта

```text
packages/
  engine/   Игровые правила, переходы состояния, подсчёт и представления для мест
  server/   HTTP API, WebSocket, пользователи, сессии и журнал команд в SQLite
  web/      React-интерфейс, Vite, настройки отображения и изображения карт
skins/      Исходные изображения для карточных оформлений
```

Движок не зависит от React и сети. Сервер применяет действия к состоянию игры и рассылает каждому игроку представление для его места, скрывая чужие закрытые карты. Клиент показывает доступные действия из серверного состояния.

### HTTP и WebSocket

Основные HTTP-маршруты:

| Метод | Путь | Назначение |
| --- | --- | --- |
| POST | `/register` | Создать пользователя: `{ name, password }` |
| POST | `/login` | Войти и получить cookie сессии: `{ name, password }` |
| POST | `/logout` | Завершить сессию |
| GET | `/me` | Получить текущего пользователя |
| POST | `/tables` | Создать стол с настройками |
| GET | `/tables/:id` | Получить сведения о столе |
| POST | `/tables/:id/join` | Занять свободное место |
| PATCH | `/tables/:id` | Изменить настройки до сдачи; доступно хозяину |
| POST | `/tables/:id/confirm` | Подтвердить договорённости приглашённому игроку |
| POST | `/tables/:id/deal` | Начать игру; доступно хозяину после подтверждений |

Кроме регистрации и входа, маршруты работы со столом требуют сессии. Ссылка интерфейса `/table/:id` отличается от HTTP API `/tables/:id`.

Клиент подключается к WebSocket по `/ws` с cookie сессии. Сообщения `watch` используются для ожидания сдачи, `join` — для подключения к игре. Игровые команды `gameAction` содержат `tableId`, `seat` (0, 1 или 2), уникальный `actionId`, `expectedVersion` и `payload.action`. Сервер также поддерживает `playCard` для отдельного состояния розыгрыша.

Сервер отправляет сообщения `table`, `snapshot` и `rejected`. Версия меняется после принятого действия. Уже обработанный `actionId` позволяет распознать повтор команды; устаревший `expectedVersion` приводит к отказу. Типы сообщений находятся в [protocol.ts](packages/server/src/protocol.ts), проверки — в [validation.ts](packages/server/src/validation.ts), HTTP-маршруты столов — в [lobby.ts](packages/server/src/lobby.ts). Входной модуль [index.ts](packages/server/src/index.ts) сохраняет экспорт существующего API сервера.

## Тестирование

Все тесты:

```sh
pnpm test
```

Отдельные пакеты:

```sh
pnpm --filter @pref/engine test
pnpm --filter @pref/server test
pnpm --filter @pref/web test
```

Используется Vitest; тесты лежат рядом с исходниками в файлах `*.test.ts` и `*.test.tsx`.

- **Движок:** колода, торговля, снос, вист, розыгрыш, мизер, распасы и подсчёт пули.
- **Сервер:** реальные HTTP-запросы и WebSocket-соединения, права на места, повтор команд, рассылка состояния и переподключение.
- **Клиент:** преимущественно статическая HTML-разметка компонентов и отдельные функции состояния и отображения. Эти проверки не заменяют взаимодействие с интерфейсом в браузере.

Проверка типов всех пакетов и сборка клиента:

```sh
pnpm typecheck
pnpm --filter @pref/web build
```

[GitHub Actions](.github/workflows/ci.yml) на push в `master` и на PR устанавливает зависимости с `--frozen-lockfile`, проверяет типы, запускает тесты и собирает клиент на Node.js 22. Это проверка изменений, а не автоматический деплой.

Добавлены регрессионные проверки независимых раздач и отсутствия закрытых данных в начальных сообщениях, восстановления после рестарта, идемпотентности, транзакционного отката, TTL, миграций, сессий, ограничений входа, Origin, heartbeat, размера/частоты сообщений и клиентского backoff.

Сквозные браузерные тесты, зависимость для измерения покрытия и минимальные пороги покрытия пока не настроены.

## Данные и ограничения

| Данные | Хранилище | После перезапуска сервера |
| --- | --- | --- |
| Пользователи и хеши паролей | SQLite, `users` | Сохраняются при сохранении файла БД |
| Сессии | SQLite, `sessions` | Сохраняются до истечения срока или выхода |
| Журнал игровых команд | SQLite, `command_log` | Сохраняется до удаления стола по TTL |
| Столы, места, настройки, состояние и обработанные команды | SQLite, `tables`, и память процесса | Восстанавливаются из снимков до истечения TTL |
| Настройки отображения игрока | `localStorage` браузера | Сохраняются в этом браузере |

Сервер рассчитан на один процесс, владеющий текущим состоянием столов. Снимки позволяют восстановиться после перезапуска, но не синхронизируют несколько одновременно работающих экземпляров. Файл SQLite содержит закрытые карты и учётные данные; не размещайте его в `STATIC_DIR` или репозитории.

Основные модули:

- Движок: `game.ts` — переходы, `game-state.ts` — создание состояния, `deal-result.ts` — результат сдачи, `proposals.ts` — предложения, `speech.ts` — речь, `hand-view.ts` — видимость карт.
- Сервер: `auth.ts`, `db.ts`, `lobby.ts`, `tables.ts`, `ws.ts`, `static.ts`, `validation.ts`, `protocol.ts`.
- Интерфейс: `GameTable.tsx` связывает компоненты `table-auction`, `table-cards`, `table-hand`, `table-trick`, `table-talon`, `table-actions`, `table-score`, `table-layout`, `table-rules` и `table-speech`. Экспорты прежнего модуля сохранены.

Оценка новых функций без их реализации — в [плане P3](docs/roadmap.md).
